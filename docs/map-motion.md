# Vehicle and camera motion

Since v1.0.9, the vehicle GeoJSON position and follow camera are rendered on the same finite timeline. Previously the GeoJSON source jumped to each incoming fix while `easeCamera(..., 700, false)` moved the map gradually, making the pointer appear to fall behind and leap forward. MapLibre documents that this camera overload uses [linear interpolation when the easing flag is false](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.maps/-map-libre-map/ease-camera.html).

The new display interpolation lasts 700 ms. One UI callback updates the vehicle point/arrow and camera target/bearing/zoom/tilt/padding at most once per 50 ms, matching the map's existing 20 FPS cap. A new fix first samples the current displayed frame, then retargets from there. Camera and marker use the same coordinate/bearing interpolation; longitude and heading take the short path around the date line and north. Camera transitions from a manually explored view interpolate from that view rather than snapping immediately onto the marker.

GPS subscription timing remains 1000 ms / 3 m. No additional location provider, sensor, service, worker thread, prediction, or background polling is added. Speed, GPS accuracy and route progress use the unmodified measured fix. First fixes, gaps over five seconds and movements over 250 m snap to the measured position instead of animating from an unrelated location. Duplicate/out-of-order, stale and invalid fixes are ignored. Once a visual transition finishes there is no recurring frame callback until another fix or explicit camera action requires it.

Exploration and route previews keep ownership of the camera while the marker can still animate. Hiding the dashboard cancels the callback and camera transition. GPS disablement and destruction also stop it. Reopening the dashboard redraws only from a fresh fix; a missing receiver update never makes the marker continue driving beyond its last measured position.

GitHub JVM tests cover first fixes, intermediate positions, early retargeting without a discontinuity, clockwise/counterclockwise north crossings, date-line wrapping, stationary targets, stopping/snapping and no overshoot. Existing tracking/heading tests cover gesture ownership, route previews and stable heading at stops. Camera/source rendering, frame costs, tilt/padding alignment, permission handoff and lifecycle behavior require physical-device checks.
